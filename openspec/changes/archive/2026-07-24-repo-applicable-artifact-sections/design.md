# Design — repo-applicable-artifact-sections

> Stage D of QRSPI. Generated 2026-07-24.
> **Implementation is BLOCKED until a human approves this file.**

## Context

Every artifact-producing QRSPI stage (Q/D/S/P/PR) stamps a fixed CRUD/web-app
skeleton into the document it generates: `## Data model`, `## API surface`,
`## Migrations`, `## Auth & authorization`, plus checklist items like "No raw
SQL in feature code" and "All new endpoints use authorization policies." In a
repo that has a database, an HTTP API, a UI, and an auth system this is
helpful scaffolding. In a markdown/Node plugin repo like this kit — which has
*none* of those surfaces — it is boilerplate that lands in every document a
human reads, and (worse) instructs the questioner to write `*Not applicable.*`
under headings that could never apply here.

The `<repo>-stack` cheatsheet (`.claude/skills/<repo>-stack/SKILL.md`, produced
by `/qrspi:stack`) is the standing record of what tech surface a repo has.
The desired end state: each stage loads the cheatsheet, derives which surfaces
the repo has, and emits **only** the sections and checklist items that carry
content for the actual surface **and** this change — omitting the rest with no
trace (PQ1/PQ2). When no cheatsheet exists, stages emit the full menu plus a
visible warning pointing to `/qrspi:stack` (PQ3). This kit gets its own
`qrspi-stack` cheatsheet so it dogfoods the fix and its artifacts actually go
clean, not merely warned (PQ7). Seven human-settled product answers (PQ1–PQ7
in `questions.md`) are FIXED inputs; this design does not re-open them.

## Goals / Non-Goals

**Goals:**
- A shared skill defines the repo-surface taxonomy and the section→surface
  mapping, loaded by all five artifact-producing agents (PQ6).
- Each of the five agents (questioner, designer, architect, planner, reviewer)
  invokes the skill and omits inapplicable sections/checklist items from its
  emitted artifact — at both repo and change level (PQ2).
- Check 3 (`TEMPLATE_CANONICAL_HEADINGS`) is reconciled with now-conditional
  headings so it neither forces CRUD headings back into skeletons nor goes dark.
- A new lint check (PQ5) guards against a re-introduced hard-coded CRUD heading,
  scoped to fenced skeleton blocks, without contradicting Check 3.
- The four templates stay consistent with the conditional-heading agents.
- A `qrspi-stack` cheatsheet for this kit declares its surface (PQ7).
- Part B (illustrative-framing fixes to `vertical-slice`/`workflow` skills),
  fixed lightly (PQ4).

**Non-Goals:**
- Building a structured stack-schema parser or a machine-readable surface DSL
  beyond the minimum the filter needs (see D3 for the deliberately-thin design).
- Making the filter a CI-enforced runtime assertion — there is no live
  cheatsheet parse at lint time (D6 bounds what the static check can assert).
- Re-litigating PQ1–PQ7.
- Changing the answer-recording format, the `PQ<N>`/`(D<n>)`/`(human)`
  conventions, or any canonical OpenSpec header (`## Context`, `## Why`, …).

## Decisions

### D1 — A new shared skill `repo-surface` owns the taxonomy + mapping; the five agents load it

PQ6 fixes "shared skill, loaded by all five agents." The open sub-question was
*which* skill. Two options:

- **(A) Expand the per-repo `<repo>-stack` skill.** Rejected: that skill is
  per-repo project scope (`.claude/skills/`), regenerated by `/qrspi:stack`, and
  varies per consumer. The filter *convention* must be kit-shipped and identical
  everywhere; it cannot live in a file the kit doesn't own.
- **(B) A new kit skill `claude/skills/repo-surface/SKILL.md` (chosen).** Ships
  with the plugin, is loaded by all five agents, and carries the surface
  taxonomy + the section→surface mapping + the omit/warn rules in one place.

The `<repo>-stack` cheatsheet remains the *data* (what surfaces this repo has);
`repo-surface` is the *logic* (how to read that data and filter a section menu).
Clean separation: data is per-repo, logic is kit-wide. This also satisfies
lint Check 2's `Load skill \`repo-surface\`` resolution once the directory exists.

### D2 — Surface taxonomy: a fixed closed list of named surfaces

`repo-surface` defines a small closed vocabulary of surface flags, each mapping
to the sections/checklist items it gates:

| Surface | Gated sections / checklist items |
|---|---|
| `data-store` | Data model, Indexing & query performance, Migrations & data; "No raw SQL"; `## Data model changes`; task "generate migration"; PR `## Migrations` |
| `http-api` | API / API surface; "endpoints use authorization policies" |
| `ui` | UI, Front-end state; `## UI surface` |
| `auth` | Auth & authorization; `## Authorization`; auth-policy checklist item |
| `typed-nullable` | "No nullable suppression (`!`) without justification" |

Sections not gated by any surface (`## Testing`, `## Sequencing & scope`,
`## Open product questions`, and the four canonical design/proposal headers)
are **always emitted** — they are surface-independent. The taxonomy is a closed
list, not open-ended: a new surface is a deliberate skill edit, which keeps the
mapping auditable and keeps the new lint check (D6) tractable.

> **Refined during stage-I dogfooding (2026-07-24):** the closed list is closed
> *by construction*, not arbitrarily — a surface exists only to gate a cluster of
> the surface-gated *sections* the agents actually emit, so the surface set
> mirrors the emitted-section set one-to-one. A surface that gates no emitted
> section would be inert. **To extend**, add the surface here *together with* the
> section(s) it gates (in the agent skeletons/templates); adding a surface alone
> has no effect. The `repo-surface` skill states this rationale so the list does
> not read as arbitrary hardcoding. Candidate future surface+section clusters are
> captured as a backlog idea (`extend-surface-taxonomy`).

### D3 — The cheatsheet stays prose; `repo-surface` reads it by a documented convention, not a schema parser

Q14/PQ7 surfaced the tension: today's `<repo>-stack` cheatsheet is *prose* under
fixed headings (`## Frameworks & key libraries`, …) with **no** structured
`has_database: false` fields. Options:

- **(A) Require structured YAML surface flags in every cheatsheet.** Rejected:
  breaks every existing consumer cheatsheet, forces a `/qrspi:stack` re-run
  across all repos, and turns a docs fix into a migration.
- **(B) `repo-surface` interprets the prose cheatsheet against its taxonomy
  (chosen).** The agent reads the loaded cheatsheet and decides each surface
  flag from its content — e.g. no database/ORM/SQL mentioned anywhere →
  `data-store: absent`. This is an LLM judgement over prose the agent already
  has in context, not a parser.
- **(C) Add an OPTIONAL structured block to the cheatsheet that overrides the
  prose inference when present (chosen as an additive complement to B).** The
  `qrspi-stack` cheatsheet this change ships (PQ7) will carry an explicit
  `## Repo surface` block naming which surfaces are present/absent, so the kit's
  own filtering is deterministic rather than inference-dependent. **`/qrspi:stack`
  is extended in THIS change (OQ2 = in-scope)** to emit this block going forward,
  so new cheatsheets across all repos are deterministic too; existing prose-only
  cheatsheets still work via (B).

**Silence semantics (Q15):** when the cheatsheet neither asserts nor mentions a
surface, treat it as **absent**, not unknown. Rationale: the whole point is to
strip inapplicable sections; a repo that has a database will mention it (ORM
dep, migrations dir, SQL). Defaulting silence to "present" would keep the CRUD
menu on exactly the docs repos this change targets. The explicit `## Repo
surface` block (C) exists for repos that want to remove any doubt.

> **Block format refined during stage-I dogfooding (2026-07-24):** the `## Repo
> surface` block is an **authoritative allowlist of the surfaces that are
> PRESENT**, not an enumeration of every surface as present/absent. A surface
> listed is present; a surface not listed is absent; when the block is present it
> is authoritative and prose inference (B) is skipped entirely. Enumerating
> surfaces as `absent` was redundant with silence=absent and read as noise
> (surfaced when a human reviewed the kit's own all-`absent` block). A repo with
> no present surfaces declares that explicitly (`_No present surfaces._`) so the
> block reads as present-but-empty rather than forgotten. This makes the block
> both cleaner and robust to a stray prose mention of an unlisted surface.

### D4 — "Omit the section" concretely = the agent skips emitting the heading and its body; the fenced skeleton is annotated, not hard-coded

Because agent inline skeletons are the runtime source of truth (research finding
#3), "omit" must be expressed in the skeleton itself. The mechanism per agent:

- The fenced skeleton's CRUD-specific headings are replaced by a **single
  conditional placeholder** with a prose instruction above the fence, e.g.
  `<!-- surface-gated sections: emit only those whose surface is present -->`
  and a compact reference to the `repo-surface` mapping — rather than ten
  literal `## Data model` etc. lines baked into the fence.
- Always-emitted headings (Testing, Sequencing & scope, Open product questions;
  the canonical design/proposal headers) stay literal in the fence.
- The prose menu (questioner step 6, designer detail-section prose) is reworded
  from "keep the heading and write *Not applicable.*" to "emit the section only
  when its surface is present and it carries content for this change; otherwise
  omit it entirely (no heading, no stanza)" — retiring the N/A convention (PQ2).

This is what lets the new lint check (D6) find zero hard-coded CRUD headings in
the fenced blocks while the surface-independent headings remain present for
Check 3 (see D5).

### D5 — Reconcile Check 3 by MOVING the CRUD headings out of its required set, not by deleting Check 3

Check 3 (`TEMPLATE_CANONICAL_HEADINGS`) currently *requires* 10 questioner
headings (incl. Data model, API, Migrations, Auth) and 4 designer headings.
Those two facts collide with this change: it must be legal for a skeleton to
*not* carry `## Data model`. Reconciliation, per template:

- **questioner (10 → 3):** keep only the surface-independent headings as
  required — `## Testing`, `## Sequencing & scope`, `## Open product questions
  (for the human)`. Drop the seven surface-gated headings (Data model, Indexing,
  API, UI, Front-end state, Auth, Migrations) from `TEMPLATE_CANONICAL_HEADINGS`.
- **designer (4 → 4, unchanged):** the four required headings are the canonical
  OpenSpec headers (`## Context`, `## Goals / Non-Goals`, `## Decisions`,
  `## Risks / Trade-offs`) — all surface-independent. No change; the four CRUD
  *detail* sections (`## Data model changes`, …) were never in Check 3's map.
- **architect proposal (4, unchanged):** `## Why / What Changes / Capabilities
  / Impact` are surface-independent. No change. (The Migrations *impact line*
  inside `## Impact` is prose within an always-present heading — gated by D4's
  emit rule, not by a required heading.)
- **architect spec-delta (3, unchanged):** ADDED/MODIFIED/REMOVED are
  operation headers, surface-independent. No change.
- **planner (0, unchanged):** already SKIP (dynamic format).

Net: Check 3's map shrinks only for the questioner, and only by removing the
seven CRUD headings. This is the minimal edit that lets skeletons drop CRUD
headings without Check 3 failing. Templates get the same seven headings
demoted from "always present" to "surface-gated" (see D8) so template and
agent stay in lockstep.

### D6 — The new PQ5 lint check (Check 11): forbid CRUD headings **inside fenced skeleton blocks** of agent files

PQ5 fixes: add a check scoped to fenced-code skeleton blocks. Concretely,
Check 11 (`checkNoCrudSkeletonHeadings`):

1. For each of the five agent files, extract fenced ```` ```markdown ```` (and
   bare ```` ``` ````) blocks from the body.
2. Assert none of a denylist of CRUD heading lines appears **as a heading line**
   inside those blocks: `## Data model`, `## Indexing & query performance`,
   `## API`, `## UI`, `## Front-end state`, `## Auth & authorization`,
   `## Migrations & data`, `## Data model changes`, `## API surface`,
   `## UI surface`, `## Authorization`, `## Migrations`.
3. Match on a line beginning with the heading marker to avoid false positives on
   prose mentions outside fences (which are legitimate — the prose menu still
   *names* these surfaces when describing the mapping).

**Non-contradiction with Check 3:** Check 3 asserts the *surface-independent*
headings are *present anywhere in the body*; Check 11 asserts the *CRUD*
headings are *absent from fenced blocks*. Disjoint heading sets (D5 removed the
CRUD headings from Check 3's required set) and disjoint scopes (whole body vs.
fenced-only). No heading is simultaneously required-present and forbidden.

**Inline vs. transitive (designer step 9 rule):** the CRUD-heading invariant is
purely inline — a heading line is baked into a fence in the file itself; there
is no shared skill/include through which a skeleton heading reaches an agent
transitively (skeletons are always literal in the agent body). So the inline
fenced-block predicate fully covers it; there is no transitive manifestation to
miss. This is called out explicitly so a future maintainer does not assume
under-coverage.

### D7 — questioner and planner gain a stack-cheatsheet + `repo-surface` load step

Research finding #4: questioner and planner do **not** load the stack cheatsheet
today. For the shared filter to work in all five agents, both need a load step
added at step 1: `Load skill \`repo-surface\` … plus the project's
stack-cheatsheet skill if it defines one.` The other three (designer, architect,
reviewer) already load the cheatsheet — they gain the `repo-surface` load only.
This does **not** widen any agent's read contract (Check 7): loading a skill is
not reading a change artifact; the banners are untouched.

### D8 — Templates: demote the seven CRUD headings to "surface-gated, emit when present"; retire the N/A instruction

`questions.template.md` is the only template with an explicit N/A instruction
("keep the heading and write *Not applicable.*"). Rewrite that comment to the
PQ2 rule: emit a section only when its surface is present and it carries content
for this change; otherwise omit entirely. Mark the seven CRUD sections as
surface-gated (a comment tag), leave Testing/Sequencing/Open-product-questions
as always-present. `design.template.md` already labels the four detail sections
"OPTIONAL" — tighten that wording to "surface-gated (omit when the surface is
absent)". `proposal.template.md`/`tasks.template.md` need only the Migrations
impact-line / migration-task note flagged as surface-gated. Templates trail
agents in authority (runtime path is the agent), but ship in the **same PR**
(Q31) so the lint heading-alignment invariant and the templates never diverge.

### D9 — Ship a `qrspi-stack` cheatsheet for this kit (PQ7) with an explicit `## Repo surface` block

Create `.claude/skills/qrspi-stack/SKILL.md` declaring: markdown
command/agent/skill/template files + a Node lint; **no** data-store, http-api,
ui, or auth. It carries the standard `/qrspi:stack` sections plus the new
`## Repo surface` block (D3-C) listing every taxonomy surface as absent. This
gives the filter a live, deterministic surface for the kit's own artifacts —
they drop the CRUD sections outright instead of only warning. Note: this file
lives under `.claude/skills/` (project scope, not shipped in the plugin), matching
where `qrspi-dogfood`/`qrspi-release` already live; it is the kit-as-consumer's
cheatsheet, not a kit-shipped skill.

### D10 — Part B (PQ4): flag the examples as illustrative, do not restructure

`vertical-slice/SKILL.md` already carries an "Illustrative only … substitute
your own stack" note on its .NET/Blazor example — light-touch is mostly done;
add one line pointing at `repo-surface` for which slice shapes apply.
`workflow/SKILL.md`'s "Anything that touches the data model, an API surface, or
auth must go through the full flow" gets a parenthetical: "(these are web-app
examples; for your repo, read the applicable surfaces from the stack
cheatsheet — a docs/plugin repo's durable-contract surfaces are its commands,
skills, and lint rules)." No structural rewrite (PQ4 "fix lightly").

## Risks / Trade-offs

- **Inference reliability (D3-B).** Deriving surface flags from prose is an LLM
  judgement and can misfire on an ambiguous cheatsheet. Mitigation: the explicit
  `## Repo surface` block (D3-C) for repos that want determinism, and the
  silence=absent default (D3) which fails toward *less* boilerplate — the visible
  failure mode is a missing section a human can add back, not silent data loss.
  **Stage-I watch-item:** confirm the `qrspi-stack` block is actually read by the
  filter in a dogfood session (no live parse exists at lint time).
- **Check 3 shrink could mask a genuinely dropped heading.** Removing the seven
  CRUD headings from Check 3's required set means the lint no longer guarantees
  a questioner *ever* emits e.g. `## API` — correct by design (that is the point),
  but it shifts responsibility for "did we consider the API surface?" onto the
  cheatsheet + `repo-surface`, not the lint. Accepted per PQ1 (cheatsheet is the
  standing record).
- **Denylist maintenance (D6).** Check 11's CRUD denylist is hand-maintained;
  a newly-invented CRUD heading spelling would slip through. Accepted — same
  class as the existing hand-maintained `TEMPLATE_CANONICAL_HEADINGS` map.
- **Two heading checks over the same files.** Check 3 (present-anywhere) and
  Check 11 (absent-in-fences) are deliberately disjoint (D6); a future edit that
  blurs the scopes could make them contradict. Mitigation: both checks carry a
  header comment stating the disjoint-set invariant.

## Vertical slices (preview)

The Structure stage will detail these; each is user-facing and demoable end to
end (a stage's generated artifact visibly loses its CRUD boilerplate):

- **Slice 1 — Filter foundation + kit cheatsheet.** Ship `repo-surface` skill
  (taxonomy + mapping + omit/warn rules) and the `qrspi-stack` cheatsheet with
  its `## Repo surface` block. Demo: the skill loads and reports the kit's
  surfaces as all-absent.
- **Slice 2 — Questioner emits repo-applicable sections.** Wire questioner (load
  step + conditional skeleton + prose reword), demote its Check 3 headings.
  Demo: run stage Q in the kit → `questions.md` has no CRUD headings, no N/A
  stanzas; run in a web-app fixture → sections reappear.
- **Slice 3 — Designer, architect, planner, reviewer emit repo-applicable
  sections.** Same treatment across the remaining four agents (detail sections,
  Migrations impact line, migration task, reviewer checklist). Demo: each
  stage's artifact goes clean in the kit, full in a web fixture.
- **Slice 4 — Lint Check 11 + templates + `/qrspi:stack` block + Part B.** Add the
  fenced-skeleton CRUD-heading check, update the four templates, extend
  `/qrspi:stack` to emit the `## Repo surface` block (OQ2 in-scope), land the
  light Part B skill edits, update README (new skill) + CHANGELOG. Demo:
  `node scripts/lint.mjs` passes; a deliberately re-added `## Migrations` in a
  fence fails Check 11.
