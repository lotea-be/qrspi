## File map

### Git-host / PR-CLI selection

- `claude/commands/pr.md` — QRSPI stage PR orchestrator (no `agent:` frontmatter; runs on the main loop). After the tasks-pass and follow-ups-pass reconciliation gates, spawns `subagent_type: qrspi:reviewer` (Agent tool) to draft the PR description. It does **not** itself resolve the host CLI by inspecting repo signals — it reads the PR-create command "named in its stack-cheatsheet" (line ~239: "Run the project's PR-create command (the host CLI named in its stack-cheatsheet -- e.g. `gh pr create` or `az repos pr create`)"). It captures stdout to extract PR number/URL, writes `openspec/changes/<id>/pr.md` (fields: PR #, URL, Title, Source branch, Target branch, Created date), and updates `openspec/backlog.md`'s row note to `in-progress (draft PR #<N> open)`. PR-create step is mode-aware per the `workflow` skill's "PR-create auto-advance" rule (Full/Semi-auto: run directly; Manual: AskUserQuestion "Create the PR now" / "Show me the description first"). No fallback host-detection logic (no `.github/`, `azure-pipelines.yml`, `.gitlab-ci.yml` signal checks) appears in `pr.md` itself — that inference logic lives only in `archive.md` and `stack.md` (below).
- `claude/commands/archive.md` — step 3 ("PR-merge gate", hard-stop) is the one place in the kit with **explicit runtime host-detection fallback logic**: "If this repo has a project-scope stack-cheatsheet skill (discoverable via Glob pattern `.claude/skills/*-stack/SKILL.md`) whose `## PR & git workflow` section documents a PR-status-query line, use that CLI and command. Otherwise infer the host from repo signals: a GitHub remote or a `.github/` directory selects `gh`; `azure-pipelines.yml` selects `az repos`; `.gitlab-ci.yml` selects `glab`; default to `gh` when none of these signals match." It then runs the resolved status-query command via the Bash tool (e.g. `gh pr view <N> --json state,url,number`, `az repos pr show --id <N>`, `glab mr view <N>`), maps host-specific "merged" states (GitHub `state == MERGED`; Azure DevOps `status == completed`; GitLab `state == merged`), and hard-stops (CLI unavailable/unauthenticated, or PR not merged) rather than proceeding silently. Step 5's "New branch + push" archive-PR-create path (`chore/archive-<id>`) reuses "the host CLI resolved in step 3 (no re-detection)" and applies the same mode-aware PR-create gate as `pr.md`.
- `.claude/skills/qrspi-stack/SKILL.md` (this repo's live cheatsheet) — carries a filled `## PR & git workflow` section (see below) that both `pr.md` and `archive.md` are meant to consult ahead of the repo-signal fallback.
- `claude/commands/stack.md` (the `/qrspi:stack` bootstrap/refresh command) — step 2's detection sweep documents the same three-way signal mapping used by `archive.md`'s fallback: "Git host & PR workflow: infer from `.git/config` (the remote URL), `.github/` (GitHub → `gh`), `azure-pipelines.yml` (Azure DevOps → `az repos`), `.gitlab-ci.yml` (GitLab → `glab`)". Step 4 is the authoritative template for the `## PR & git workflow` section it writes into the generated cheatsheet (see Stack-cheatsheet structure below).
- `openspec/specs/archive-workflow/spec.md` (base spec, lines ~74-95, ~315-322) — codifies the archive-workflow's host-inference requirement in the same three-way form (GitHub remote/`.github/` → `gh`; `azure-pipelines.yml` → `az repos`; `.gitlab-ci.yml` → `glab`; default `gh`) and a scenario for the no-stack-cheatsheet fallback path. Also documents "Archive PR is auto-created on the new-branch path" requiring `git push -u origin chore/archive-<id>` to succeed first, using the already-resolved host CLI (no re-detection) and the stack-cheatsheet's `## PR & git workflow` default-target-branch value.
- `openspec/specs/qrspi-run-mode/spec.md` (lines ~166-193) — "PR-create is auto-executed in Full and Semi-auto mode" requirement/scenario, and the hard-stop set (condition 2: "a `git commit` or `git push` failure, including a dirty or conflicted working tree or a rejected remote push") with a worked scenario: "GIVEN Full auto mode is active and the Q stage has committed / WHEN `git push` returns a non-zero exit code (e.g. remote rejects the push) / THEN the orchestrator stops the chain, reports the git error to the human, and does NOT auto-advance."

### Assumption of a remote / origin

Grep across `claude/commands/*.md` and `.claude/skills/*/SKILL.md` for `git push`, `origin`, `gh pr`, `az repos`, `glab`, `.github/`, `azure-pipelines.yml`, `.gitlab-ci.yml` surfaces these call sites:

- `claude/commands/questions.md:36` — `git push -u origin <branch>` (unconditional; run immediately after branch creation, step 2, with no existence check on `origin` and no failure-handling branch described inline — relies on the canonical hard-stop procedure in `workflow` for any git failure).
- `claude/commands/implement.md:114,120,172` — three `git push` sites (per-slice commit steps and a final commit step), each following the canonical *commit step* choreography from the `workflow` skill (no explicit remote-existence check inline; failures are hard-stop condition 2).
- `claude/commands/pr.md:291` — `git push` in the final "record PR link" commit step; also the PR-create call (`gh pr create` / `az repos pr create`, line ~239) which inherently requires the change to already be pushed to a remote for the CLI to open a PR against.
- `claude/commands/archive.md:188,219` — `git push -u origin chore/archive-<id>` (new-branch path) and a plain `git push` (commit-to-main path); also `gh pr create` / `az repos pr create` / `glab mr create` (lines ~190-202) for the archive PR.
- `claude/commands/retro.md:48` — one `git push` in its commit step (not otherwise detailed here; out of the explicitly-named areas but caught by the grep).
- `.claude/skills/qrspi-release/SKILL.md` — several `git push origin main` / `git push origin vVER` calls, plus preconditions that assert the repo is "in sync with origin" (`git fetch origin` then compare `main` to `origin/main`) before releasing. Dev-tooling skill, not shipped in the plugin.
- `.claude/skills/qrspi-marketplace-bump/SKILL.md` — `git ls-remote --tags origin <TAG>`, `git pull --ff-only origin main`, `git push -u origin chore/bump-qrspi-<TAG>`, `gh pr create -R lotea-be/ai-agent-marketplace ...`. Dev-tooling skill operating on a sibling marketplace repo, not shipped in the plugin.
- The canonical *commit step* procedure in skill `workflow` (loaded by every stage command) ends every branch (Full/Semi-auto and Manual) with a bare `git push` after `git add`/`git commit`, and defines hard-stop condition 2 as "Any non-zero git exit code during the auto-commit step" — this is the single shared mechanism through which every stage's push failure (including a missing/misconfigured `origin`) is surfaced, rather than each command re-implementing its own remote check.
- No command body in the kit contains a conditional branch for "no `origin` remote configured" or "remoteless repo" — every `git push` site above is written as an unconditional command whose only documented failure path is the generic git-error hard-stop.

### Kit skill registry and loading

- `scripts/skill-sets.mjs` — pure-data module (no Node built-in imports), the single source of truth for two exported registries, imported by both `scripts/lint.mjs` (Check 2b) and `scripts/context-footprint.mjs`:

### Lint gate structure

- `scripts/lint.mjs` — single file, 4135 lines, Node built-ins only (`node:fs`, `node:path`, `node:url`; no npm deps, matching the "No npm runtime dependencies" dependency policy). Structure:
  - Each Check is an `async function checkXxx(errors) { ... }` that receives the shared `errors` array (declared once in `main()`) and pushes formatted violation strings into it, each prefixed with a bracketed tag (e.g. `[migration]`, `[researcher-gate-instruction]`) identifying which check raised it. Some check functions additionally `return` a count/status (not uniformly used for aggregation — the authoritative pass/fail signal is `errors.length` at the end of `main()`).
  - On success a check prints a one-line `  OK: ...` confirmation via `process.stdout.write`.
  - `main()` (the file's only top-level driver) prints a per-check header line (`Check N: <label>\n`) immediately before `await`-ing that check's function, in strict ascending order 1 → 24 (with sub-labelled variants like `Check 2b`, `Check 10 (budget-gate-embed)`, `Check 10b` interleaved at their historical insertion points — check numbers are not always contiguous integers; some are lettered sub-checks documented inline as "Registered after Check N" in header comments near each check's implementation).
  - After all checks run, `main()` reports `All checks passed.` (exit 0) if `errors.length === 0`, else prints the violation count and every message, then `process.exit(1)`.
  - Current registered checks (24, some multi-part): 1 Pin agreement, 2 Frontmatter/name resolution, 2b Skill-set registry, 3 Heading alignment, 4 README command coverage, 5 Gate-tool/executor agreement, 6 Migration manifest presence+schema+marker format, 7 Read-contract banner agreement, 8 PR reconciliation passes structure, 9 Version-check embed, 10 (budget-gate-embed) Budget-gate embed, 10b Triage path anchors, 11 No surface-gated skeleton headings in fenced blocks, 12 Output-contract banner presence, 13 Compute annotation value-validation, 14 Surface applicability of artifact headings, 15 Implementer variant agent drift gate, 16 Followup bare-stem guard, 17 Helper agent read-contract banner agreement, 18 Modified scenario count guard, 19 Authoritative sync delegator, 20 Requirement first-line MUST/SHALL guard, 21 Format-rules parity guard, 22 Backlog schema guard, 23 Backlog wikilink resolution, 24 Researcher gate-instruction presence.
  - Shared helpers used across checks: `readFileOr(path, fallback)` (async file read with a fallback on failure — used pervasively instead of raw `fs.readFile` + try/catch inline), `semverCmp(a, b)` (numeric SemVer tuple comparator, documented as load-bearing because lexical sort misorders `0.9.0` vs `0.10.0`), `parseManifestYaml(text)` / `applyItemField(item, key, val)` (a minimal dependency-free YAML extractor purpose-built for the migration-manifest schema — not a general YAML parser), and repeated fence-scan patterns (open/close tracking for fenced code blocks) reused by Checks 11, 14, and 20 (each documented inline as mirroring the prior check's approach).
  - Adding a new Check involves: (1) writing `async function checkNewThing(errors) { ... }` following the `errors.push('[tag] ...')` / `OK:` convention; (2) inserting an `await checkNewThing(errors);` call in `main()` at the appropriate position with a `process.stdout.write('\nCheck N: <label>\n')` header immediately before it; (3) choosing a check number/letter that reflects insertion order relative to existing checks (the file's top-of-file comment block documents each check's "Registered after Check N" relationship — this convention is maintained by hand, not generated); (4) if the new check depends on a helper (e.g. fence-scanning, SemVer comparison), reusing the existing shared helper rather than re-implementing it, per the file's own cross-references (e.g. "mirrors Check 11's approach").

### Migration manifest mechanics

- `migrations/*.yaml` — nine files present: `0.6.0` (floor), `0.7.0`, `0.8.0`, `0.9.0`, `0.10.0`, `0.10.1`, `0.11.0`, `0.12.0`, `0.13.0`. Schema (enforced by lint Check 6, `checkMigrationManifests`, and documented authoritatively in `claude/skills/qrspi-update/SKILL.md`): top-level keys `version` (bare SemVer matching the filename stem), `summary` (always present, YAML block scalar `>` or plain string), `automated` (list, possibly empty), `manual` (list, possibly empty).
  - `automated[]` items: `action` (closed vocabulary — `edit-file` is the *only* legal value; any shell-requiring step must instead be authored as `manual`), `path` (must start with `openspec/` — the walk never edits outside the consumer's `openspec/` directory), `description`, plus exactly one edit-pattern key set (`find`+`replace`, `find_all`+`replace`, `insert_after`+`content`, `insert_before`+`content`, `append`+`content`, `prepend`+`content`, or `overwrite`+`content`), plus two optional idempotency fields: `skip_if_contains` (non-empty string; whole-file substring pre-check that short-circuits the step if already applied) and `anchor_missing: warn-and-skip` (closed literal; degrades a missing-anchor hard-stop into a warn-and-continue).
  - `manual[]` items: just a `description` string; surfaced to the human via `AskUserQuestion` ("Done -- continue" / "Stop here -- I'll resume the walk manually") rather than applied automatically.
- `migrations/0.13.0.yaml` (worked example) — one `automated` step: an `edit-file` / `insert_after` step on `path: openspec/backlog.md`, carrying both `skip_if_contains` (the legend-comment marker text) and `anchor_missing: warn-and-skip`, inserting a "Backlog schema legend" comment block after the `# Backlog` title line. Four `manual` steps (plain-string descriptions, no `action` field): add missing `## In progress` / `## Proposed` / `## Ideas` headings if absent; add the P-band preamble under `## Ideas` if absent; add missing `**Why:**` / `**Shape:**` lines to standalone `idea`/`proposed` rows; and (edge case) run `/qrspi:init` if `openspec/backlog.md` is entirely absent.
- `claude/commands/update.md` (`/qrspi:update`) — runs on the **main-loop orchestrator** (no `agent:` frontmatter), explicitly because its manual-step gates use `AskUserQuestion`, which is unavailable inside a subagent. Accepts an optional `<target-version>` bare-SemVer argument; delegates all logic to the `qrspi-update` skill.
- `claude/skills/qrspi-update/SKILL.md` — the authoritative logic, in two documented sections (explicitly "do not fold apply logic into the read path"):
  - **Read path:** resolves target `B` (explicit-argument first when given, else auto-detect from the installed plugin's `plugin.json` version or the highest shipped `migrations/<v>.yaml` — flagged as an "UNVERIFIED" OQ1 watch-item because there is no portable primitive for a command body to learn its own plugin-install directory across machines/OSes); reads marker `A` from `openspec/.qrspi-version`; handles three edge cases before walking — already-up-to-date (`A == B`, no-op), no-marker-present (`AskUserQuestion`: initialize marker to `B` vs. supply real `A`), and downgrade (`A > B`, hard-stop, no reverse migrations); then builds the ordered walk list by Glob-enumerating `migrations/*.yaml`, filtering to `A < v <= B`, and sorting by **numeric** SemVer tuple comparison (explicitly not lexical — `0.9.0` must sort before `0.10.0`). Prints a plan preview (version, summary, automated/manual counts) before applying.
  - **Apply phase:** per version, ascending, all `automated` steps first then all `manual` steps gated by `AskUserQuestion`. `edit-file` dispatcher: guards `action == 'edit-file'` and `path` starts with `openspec/` (hard-stop otherwise); applies exactly one edit pattern; writes via Read+Write/Edit tools; prints a one-line confirmation without asking. Marker bump (`openspec/.qrspi-version` = `B`, Write tool, single bare-SemVer line) happens only after the LAST step of the LAST version completes — a partial/aborted walk (any hard-stop or "Stop here" choice) must NOT bump the marker. Final stage-and-print-commit tail: `git add openspec/.qrspi-version [<edited paths>]` (explicit paths, never `-A`), then prints (but does NOT run) a `git commit -m "chore: apply qrspi-update migrations to v<B>"` command — the human owns the commit.

## Implicit contracts and conventions

- **Stack-cheatsheet-first, repo-signal-fallback is the consistent pattern for host/CLI resolution.** Every place that needs a PR-create or PR-status CLI (`pr.md`, `archive.md`, `stack.md`'s own detection sweep) prefers a project-scope stack-cheatsheet's `## PR & git workflow` fields when present, and only falls back to inspecting repo signals (`.github/`, `azure-pipelines.yml`, `.gitlab-ci.yml`, git remote URL) when no cheatsheet (or no relevant field) exists. Only `archive.md` currently spells out the full three-way signal-inference fallback inline; `pr.md` assumes the cheatsheet is present and does not itself repeat the fallback logic.
- **No command body shells out for repo inspection** — the kit convention (stated in `CLAUDE.md`) is to use the Glob tool instead of exclamation-prefixed shell-injection lines, both for functional reasons (cross-platform) and to avoid tripping the static permission scanner. Host-CLI *invocation* itself (`gh pr view`, `git push`, etc.) is explicitly called out as "a Bash-tool invocation, not literal shell-injection syntax in this file" in `archive.md`.
- **Git-failure handling is centralized, not per-call-site.** No individual `git push` / PR-create call site in any command body contains its own error-branching logic; all rely on the shared hard-stop procedure defined once in skill `workflow` (condition 2: any non-zero git exit code) and the mode-aware commit-step choreography (also defined once in `workflow`) rather than re-implementing retry/fallback logic locally.
- **`origin` is always assumed to exist and be writable** wherever `git push` appears; no command checks for the remote's existence, name, or reachability before pushing. The single point where remote-in-sync-ness IS explicitly checked is the (dev-tooling, not-shipped) `qrspi-release` skill's precondition ("`git fetch origin` then confirm `main` is level with `origin/main`").
- **Migration manifests are a closed, defensively-validated schema.** Both the lint gate (Check 6) and the runtime `/qrspi:update` walker independently re-validate the same constraints (`action` closed to `edit-file`, `path` must be `openspec/`-scoped, no shell steps ever automated) — the skill's prose explicitly notes "The kit's lint enforces this; the walk assumes it holds" but still re-guards defensively at runtime.
- **Every new file/skill/agent surface in this kit has a matching lint Check and/or registry entry**, and additions are expected to touch multiple sites atomically (skill loading touches `SKILL_SET_EXPECTED`; new surfaces touch the `repo-surface` skill's taxonomy table + agent skeleton gate comments + Check 11/14 denylists/heading-maps + the `qrspi-stack` `## Repo surface` block, per that skill's own "Extending the taxonomy" checklist).
- **Command-vs-subagent split governs where `AskUserQuestion` can be used.** Any command that needs interactive human gates (`update.md`, and by extension anything that would need to ask the human about git-host/remote ambiguity) must run on the main-loop orchestrator (no `agent:` frontmatter), never inside a spawned subagent.

## Notable discrepancies
- `pr.md`'s prose says the PR-create CLI is "named in its stack-cheatsheet" but does not itself carry the GitHub/.github/, azure-pipelines.yml, .gitlab-ci.yml repo-signal fallback logic that `archive.md` spells out explicitly for the same host-resolution problem — the fallback exists in only one of the two command bodies that need it (though `archive.md`'s step-5 archive-PR-create path explicitly reuses "the host CLI resolved in step 3 (no re-detection)", so within `archive.md` itself the two PR-create call sites are consistent).
- The migration-manifest schema (per both `qrspi-update`'s prose and lint Check 6) restricts every `automated` step's `action` to `edit-file` only and every `path` to `openspec/`-scoped — i.e. the existing migration mechanism has no built-in primitive for an automated step to touch a non-`openspec/` file (e.g. a project-scope `.claude/skills/<repo>-stack/SKILL.md`); any such change is necessarily a `manual` step today.
